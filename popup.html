Type 3 uses invisible characters. Most login forms will accept it, but some may reject or mangle it. If a site rejects your new password, switch back to Type 1 or 2 and generate again.

Type 4 draws from ~94,500 base characters (CJK, Hangul, dozens of scripts, box-drawing/braille/emoji blocks, ...) plus a wide modifier and Private-Use set — ~25.7 bits of entropy per symbol. Almost certainly too exotic for real login forms; treat this as a vault-only / theoretical-maximum tier, not something to type into a typical website.

Type 5 draws from essentially the entire valid Unicode codespace (~1.1 million codepoints, ~29.8 bits of entropy per symbol) — everything Type 4 has, plus every other assigned script and symbol, and even currently-unassigned reserved codepoints. It still excludes control characters, the space character, lone surrogates, and official Unicode noncharacters — not as a style choice, but because those genuinely cannot be represented or safely stored as ordinary text. This will almost certainly be rejected by real login forms — it exists as the theoretical ceiling, mainly for a vault or as a cryptographic key/seed, not for typing into a website.

Type 6 stacks up to 3 independent Unicode modifiers (variation selectors & combining marks) onto every base codepoint from the full valid Unicode codespace — ~47.6 bits of entropy per symbol (~12,186 bits at length 256). Designed strictly for offline master keys, disk encryption, and vaults — websites will almost certainly reject it.

Checked categories above and anything typed below are merged into one alphabet — use either, or both together. In the text field, each space/comma-separated token is read independently, so ranges and literal characters can be freely mixed: U+0400-U+04FF is read as a range, while any other token contributes its distinct characters directly. Control characters, lone surrogates, and Unicode noncharacters are always filtered out regardless of what you enter or check. Minimum digit/special guarantees aren't available in Custom mode — you get exactly what you selected/typed, nothing added.

⚠️ Setting either minimum above 0 slightly reduces entropy (some positions become predictably "at least this many digits / special chars" instead of fully free choice). Leave both at 0 for maximum entropy; raise them only if a specific site requires it. "Classic special characters" means standard ASCII punctuation (! @ # $ % ^ & * ( ) - _ = + [ ] { } | ; : ' " , . < > / ? etc.) — available at every complexity level except custom Type 6.

When checked, each generation sends a request to two public randomness services — the ANU Quantum RNG and the drand public randomness beacon — over HTTPS. This does leave your browser: the request reveals your IP address and the timing of that request to those two operators (nothing else — no password data, no other content, is ever sent). Their response is never used on its own: it's combined with fresh local CSPRNG bytes through one HMAC-SHA256 extract-and-expand step (a standard HKDF-style construction), so the final result is at least as strong as local-only generation even if you don't trust either service — querying them can only add uncertainty, never remove it. Uncheck this to generate from local entropy only, with no network request at all (this is verified by an automated test — see tests/network-entropy.test.js if you want to check for yourself).

On by default. This only changes the final ordering of the characters already chosen (a re-shuffle, using fresh local entropy, no network) — it never removes or replaces a character, so it doesn't reduce which characters end up in the password, only avoids an obviously-patterned arrangement of them. With a very small alphabet (e.g. a 2-character custom Type 6 set) this may not always be possible; the status message will say so if it happens.

Every password already mixes local CSPRNG entropy through one HMAC-SHA256 extraction (plus the ANU QRNG and drand beacon too, if the checkbox above is on). With Deep-mix on, generation re-draws fresh local entropy and folds it in again before producing each character (when network entropy is also on, network reshakes are additionally capped at 8 rounds to respect QRNG rate limits, then it continues reshaking with local entropy only). This is a genuine defense-in-depth measure — it protects against one seed source turning out to be predictable — rather than a fundamental increase in entropy: a single well-seeded HMAC expansion is already cryptographically indistinguishable from independent randomness per block. Off by default; adds a little latency for long Type 3 passwords.

Copies the generated password straight to your clipboard instead of requiring a focused field on the page. Note that most clipboard managers/history tools will retain whatever you copy — this doesn't change that, it's a property of the clipboard itself, not something TrueGen can control.

Reads the field's current value and estimates its composition and a rough entropy figure — nothing is sent anywhere, this is a local, heuristic guess (see the result text for caveats), not a certified security score. Doesn't touch the field's contents.

🔐 Split & store separately

Splits the generated password into pieces (Shamir secret sharing) across the locations you check below, instead of storing it whole anywhere. Any one piece alone is mathematically indistinguishable from random noise — see the README for exactly which threat this does and doesn't protect against, and why "Cloud" and "Manual" are NOT interchangeable despite both being "not on this device".

Backs up your local split pieces (and their public metadata — labels, sites, thresholds) so they survive a browser reinstall or profile switch. Contains no raw share bytes — the local piece stays encrypted by its PIN inside the export file, so the file alone is safe, but treat it with the same care as any backup: still specific to your splits, still worth not handing to someone you wouldn't trust with the metadata (which sites you use this feature for). Does not include Cloud shares (already backed up via Firefox Sync) or Manual codes (never stored anywhere to begin with — that's the point).

Replaces the external HMAC-SHA256 tag with an internal integrity trailer inside the polynomial. Disables Local/Cloud storage so < k shares leak strictly 0 bits.

Each name here gets its OWN unique code — not a shared code. With a threshold below "all", any that many of these people together can reconstruct the password, but no smaller group (and no single one of them) can. Leave all blank to skip Manual entirely.

Check at least 2 locations total (Local counts as one; each named Manual holder counts as one; Cloud counts as one). Local protects against someone stealing this device (useless to them without your PIN). Manual is the only one that protects against being forced to unlock everything on this device — it only works if each holder actually keeps their code somewhere separate from this device (and, for multiple holders, separate from each other). Cloud only protects against losing this one device (it reappears automatically once you're signed into Firefox Sync anywhere) — it is not a coercion-resistant location, since signing in recovers it.

Never stored anywhere, including by TrueGen — if you forget it, the local piece is permanently unrecoverable (that's the point: nothing here can "reset" it for you, that would defeat its purpose). A short PIN is faster to type but weaker against someone who steals the encrypted piece and attacks it offline at their leisure — a longer passphrase is meaningfully stronger for the same reason your generated passwords are long.

TrueGen never stores, transmits, or logs the passwords it generates. Each password is created locally and written directly into the field you had focused — it exists only in your browser's memory and, if you save it, in Firefox's own password manager. Tip: you can also right-click any editable field and choose "Fill password (TrueGen)" from the context menu for a quick length/complexity picker right on the page.
